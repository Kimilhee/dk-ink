# 지우개 상호작용 PRD

- 상태: 구현 및 검증 중
- 기준 버전: 0.0.19
- 대상: 터치와 스타일러스를 동시에 사용하는 드로잉 플레이그라운드

## Problem Statement

사용자는 왼손으로 플로팅 도구 모음을 조작하면서 오른손의 스타일러스로 자연스럽게 필기하고 싶다. 그러나 손가락 터치가 간헐적으로 선택되지 않거나, 손가락을 지우개 아이콘에 계속 대고 있는데도 스타일러스 한 획이 끝난 뒤 펜으로 돌아가는 문제가 있다.

브라우저는 손가락과 스타일러스 입력을 각각 Pointer Events와 Touch Events로 전달하며, 팜 리젝션 과정에서 손가락 스트림을 취소하거나 입력 식별자를 재사용할 수 있다. 따라서 단순히 숫자 식별자나 스타일러스 획 종료만으로 손가락 해제를 판단하면 안 된다.

## Solution

도구는 토글이다. 누른 도구가 선택된 채로 남고, 다른 도구를 눌러야 바뀐다.

| 사용 동작                                        | 결과                                                |
| ------------------------------------------------ | --------------------------------------------------- |
| 도구 버튼을 손가락이나 스타일러스로 누름         | 펜↔지우개가 뒤바뀌고 그대로 유지된다.               |
| 전환 방식을 `호버`로 두고 포인터가 버튼에 들어옴 | 들어오는 순간 펜↔지우개가 뒤바뀐다.                 |
| 전환 방식을 `호버`로 두고 버튼을 탭함            | 탭으로는 바뀌지 않는다(두 번 뒤집히는 것을 막는다). |
| 지우개로 여러 획을 지움                          | 획 수와 관계없이 지우개를 유지한다.                 |
| 같은 입력이 `pointerdown`과 `touchstart`로 중복  | 한 번만 전환한다(시간창으로 중복을 거른다).         |
| 스타일러스가 화면에 근접(호버)해 있음            | 도구 모음을 회색으로 표시해 손가락이 막힘을 알린다. |
| 스타일러스가 도구 모음 위에 호버함               | 그 펜으로 누를 수 있으므로 회색으로 바꾸지 않는다.  |
| 스타일러스가 호버 범위를 벗어남                  | `pointerout` 즉시 회색을 푼다(타이머는 폴백).       |

펜과 지우개는 버튼 하나를 번갈아 눌러 쓴다. 두 아이콘이 항상 함께 보이고 활성 쪽만 파랑,
비활성은 회색이라 무엇에서 무엇으로 바뀌는지 한눈에 들어온다.

"누르고 있는 동안만 지우개"라는 순간 전환을 손가락 홀드와 S펜 측면 버튼 두 방식으로 시도했으나
대상 기기에서 어느 쪽도 성립하지 않았다. 경위와 각각이 막힌 이유는 Further Notes 참고.

## User Stories

1. 왼손잡이 보조 조작 사용자로서 왼손으로 도구를 바꾸고 오른손으로 스타일러스를 사용하고 싶다. 그래야 필기 흐름을 끊지 않고 지울 수 있다.
2. 사용자로서 지우개를 누르는 즉시 지우개가 활성화되길 원한다. 그래야 별도의 탭 완료를 기다리지 않고 바로 지울 수 있다.
3. 사용자로서 지우개를 한 번 선택하면 여러 획을 연속으로 지우고 싶다. 그래야 매 획마다 지우개를 다시 선택하지 않아도 된다.
4. 사용자로서 선택한 도구가 내가 바꾸기 전까지 유지되길 원한다. 그래야 도구가 임의로 바뀌지 않는다.
5. iPad 사용자로서 팜 리젝션이 입력 스트림을 취소해도 선택한 도구가 임의로 바뀌지 않길 원한다. 그래야 기기별 이벤트 차이 때문에 필기가 중단되지 않는다.
6. 스타일러스 사용자로서 스타일러스의 Touch 이벤트가 손가락 이벤트로 오인되지 않길 원한다. 그래야 입력 종류에 따른 판정이 서로 어긋나지 않는다.
7. 사용자로서 손가락과 스타일러스가 같은 숫자 식별자를 재사용해도 올바른 도구가 유지되길 원한다. 그래야 브라우저 내부 식별자 관리 방식에 영향을 받지 않는다.
8. 사용자로서 펜 버튼을 누르면 언제든 펜으로 돌아가길 원한다. 그래야 명시적으로 도구를 바꿀 수 있다.
9. 키보드 사용자로서 도구 버튼을 키보드로 선택할 수 있길 원한다. 그래야 터치 외 입력 방식에서도 같은 도구 상태를 사용할 수 있다.
10. 사용자로서 현재 선택된 도구가 짙은 파란색으로 즉시 표시되길 원한다. 그래야 입력이 정상적으로 인식됐는지 바로 확인할 수 있다.
11. 테스터로서 현재 배포된 버전을 화면에서 확인하고 싶다. 그래야 수정본이 기기에 반영됐는지 판단할 수 있다.
12. 유지보수자로서 동작 변경마다 패치 버전이 증가하길 원한다. 그래야 사용자 테스트 결과를 정확한 코드 버전과 연결할 수 있다.
13. 호버 지원 스타일러스 사용자로서 펜이 화면 가까이 떠 있어 손가락 터치가 막히는 동안에는 도구 모음이 회색으로 바뀌어 지금 손가락이 안 먹는 상태임을 바로 알고 싶다. 그래야 눌리지 않는 아이콘을 반복해서 누르며 헤매지 않는다. 단 펜이 도구 모음 위에 있을 때는 그 펜으로 누를 수 있으므로 회색으로 바뀌지 않아야 한다.

## Implementation Decisions

- 도구 선택은 토글이며 별도의 상태 모듈 없이 `editor.tool` 하나로 표현한다. 홀드·복귀 같은
  중간 상태가 없으므로 접촉 식별자를 추적할 이유도 없다.
- 도구 모음은 가로로 놓고 화면 아래 가운데를 기본 위치로 삼는다. 손가락으로 조작하지 않는
  전제라 세로로 세워 둘 이유가 없고, 가로 쪽이 필기 영역을 덜 가린다.
- 아이콘은 글리프 대신 CSS 도형이나 SVG로 그린다. 이모지 성격을 가진 문자(예: `⚙`)는
  `font-variant-emoji: text`나 이형 선택자(U+FE0E)를 붙여도 기기에 따라 컬러 이모지로
  렌더링된다 — 실제로 같은 아이콘이 한 기기에서만 연두색으로 나왔다.
- 펜·지우개를 버튼 하나로 합치고 두 아이콘을 함께 보여준다. 아이콘이 하나만 보이면 그것이
  현재 상태인지 누르면 될 상태인지 헷갈리기 때문이다. 활성 쪽만 파랑, 비활성은 회색으로
  칠한다 — 배경을 칠하지 않고 아이콘 색만 바꿔야 둘의 대비가 그대로 드러난다.
- 도구 전환을 일으키는 입력은 설정에서 `탭`과 `호버` 중 고른다. 기본은 `탭`이다. 스타일러스로
  필기하는 동안 손가락이 막히는 기기에서는, 펜을 버튼 위로 가져가는 것만으로 바꾸는 편이
  빠르기 때문이다.
- 두 방식은 배타적으로 동작한다. 동시에 켜면 호버 상태에서 버튼을 탭할 때 `pointerenter`와
  `pointerdown`이 잇따라 들어와 두 번 뒤집히고 제자리로 돌아온다.
- 호버 감지는 `pointerenter`가 아니라 `pointermove`의 좌표로 한다. `pointerenter`가 의미상
  더 맞지만 스타일러스 호버에서는 기기에 따라 오지 않아 전환이 아예 일어나지 않았다.
  `pointermove`는 호버 중에도 꾸준히 들어오므로, 직전 안팎 여부를 기억해 경계를 넘어선 첫
  이벤트에서만 반응한다.
- 도구를 지정하는 대신 뒤집는 동작이므로 **멱등이 아니다**. 같은 입력이 `pointerdown`과
  `touchstart` 양쪽으로 들어오면 두 번 뒤집혀 제자리로 돌아오므로, 중복을 걸러내는
  `activateOnPress`로 배선한다. 도구 버튼과 동작 버튼을 나눴던 헬퍼는 하나로 합쳐졌다.
- 도구 모음의 입력은 `click`을 기다리지 않고 `pointerdown`과 `touchstart`에서 바로 처리한다.
  스타일러스가 둘 중 어느 쪽으로 들어올지 기기마다 달라, 한쪽만 걸러 받으면 특정 기기에서
  스타일러스나 손가락 입력이 아예 무시된다.
- 되돌리기·다시 실행·전체 지우기·설정처럼 상태를 토글하거나 누적하는 버튼은 중복 호출이
  안전하지 않으므로(같은 입력이 두 번 들어오면 두 번 실행된다), 짧은 시간창으로 중복 호출을
  걸러낸 뒤 실행한다.
- 막힌 손가락 터치 자체는 웹 페이지가 관찰할 수 없다(OS/디지타이저가 브라우저까지 이벤트를
  보내지 않는다). 대신 원인인 스타일러스 호버는 관찰할 수 있다 — 호버 중인 펜은 화면에
  닿지 않아도 `pointerType: "pen"`인 `pointermove`를 계속 낸다. 이 호버가 유지되는 동안
  아이콘을 회색 처리해서 "지금은 손가락이 안 먹는 상태"를 색으로 알린다. 글로 길게
  설명하는 안내 배너보다, 실제 상태와 계속 연동되는 시각 신호가 낫다.
- 선택된 도구는 색과 밑줄 두 가지로 표시한다. 펜이 근접해 색이 죽는 동안에도 어느 쪽이
  선택됐는지 알아볼 수 있어야 하기 때문이다. 밑줄은 아이콘이 아니라 아이콘을 감싼 슬롯에
  긋는다 — 아이콘에는 회전(지우개)과 좌우 반전(펜) 변형이 걸려 있어 거기에 선을 그으면
  같이 기울어진다.
- 회색 처리는 도구 모음 배경이 아니라 **아이콘에만** 건다. 판 전체가 물들면 시야에서 계속
  거슬리는 데 비해, 아이콘만 죽여도 신호로 충분하다. 활성 아이콘은 진한 회색으로 남겨
  비활성과의 구분은 유지한다.
- 펜이 호버 범위를 벗어나는 순간 `pointerout`이 `relatedTarget: null`로 들어오므로, 이걸 듣고
  즉시 회색 처리를 푼다(엘리먼트 사이 이동은 `relatedTarget`이 채워져 있어 구분된다). 마지막
  펜 이벤트 이후 700ms 타이머는 이 이벤트를 보내지 않는 기기를 위한 폴백으로만 남긴다 —
  타이머에만 의존하면 화면의 포인터는 이미 사라졌는데 회색이 0.5초쯤 늦게 풀린다.
- 펜이 도구 모음 위에 떠 있는 동안에는 회색 처리를 하지 않는다. 회색은 "여기는 지금 누를 수
  없다"는 뜻인데, 그 자리의 펜은 실제로 아이콘을 누를 수 있어 신호가 사실과 어긋난다.
- 패키지 버전을 단일 진실의 원천으로 사용하며 화면 상단 버전 표시는 같은 값을 빌드 시 가져온다.
- 이번 변경은 `0.0.19`이며, 이후 사용자에게 전달되는 동작 수정마다 SemVer 패치 번호를 1씩 올린다.

## Testing Decisions

- 테스트는 내부 필드가 아니라 외부에서 관찰 가능한 도구 전환 결과를 검증한다.
- 도구 선택이 토글로 단순해지면서 별도 상태 모듈과 그 단위 테스트는 제거했다. 남은 동작은
  이벤트 리스너 배선이라 단위 테스트로 잡을 것이 없고, 편집기 자체의 테스트가 도구별 동작을
  이미 덮는다.
- 기존 편집기 테스트 방식과 동일하게 빠르고 결정적인 단위 테스트를 우선한다.
- 실제 기기 수동 승인 테스트: (1) 손가락으로 지우개·펜을 번갈아 선택해 매번 즉시 바뀌는지,
  (2) 스타일러스가 화면에 근접하면 도구 모음이 회색이 되고 멀어지면 즉시 풀리는지,
  (3) 펜이 도구 모음 위에 있을 때는 회색이 되지 않는지 확인한다.
- 배포 워크플로에서 포맷, 타입 검사, 전체 테스트, 플레이그라운드 빌드를 통과해야 한다.

## Out of Scope

- 스타일러스 더블 탭을 지우개 전환에 연결하는 기능
- 지우개 버튼을 누르지 않은 상태에서 팜 입력을 별도 제스처로 사용하는 기능
- 손가락으로 캔버스에 직접 필기할 때의 팜 리젝션 정책 변경
- 지우개 모양, 색상, 애니메이션의 추가 디자인 변경
- 도구 선택 상태의 영구 저장 또는 기기 간 동기화
- 라이브러리 공개 API에 순간 지우개 상태를 추가하는 작업

## Further Notes

- 웹 브라우저가 취소한 손가락 스트림에서는 물리적인 접촉 상태를 완전히 관찰할 수 없으므로, 취소 이벤트 자체를 해제 신호로 사용하지 않는다.
- 버전 표시는 사용자가 캐시된 이전 배포본과 수정된 배포본을 구분하기 위한 승인 기준이다.
- 이 PRD는 로컬 문서로만 관리하며 이슈 트래커에는 게시하지 않는다.
- **원인 확정, 해결은 안내로 대체**: 일부 S펜 지원 안드로이드 기기(예: 삼성 갤럭시탭 A
  계열)에서 스타일러스가 화면에 닿지 않고 근접만 해도(호버) 화면에 포인터가 뜨는데, 이
  포인터가 떠 있는 동안은 디지타이저/OS가 손가락 터치 이벤트를 브라우저까지 아예 보내지
  않는다는 것을 사용자가 직접 확인했다. 웹 페이지 JS는 이미 도착한 이벤트만 다룰 수 있어
  애초에 도착하지 않는 이벤트는 되살릴 방법이 없다 — 즉, 이 현상 자체는 코드로 고칠 수 없다.
  0.0.5에서는 안내 배너에 "펜으로 아이콘을 탭하라"는 대안을 넣었는데, 이건 이 PRD가 애초에
  풀려는 문제(왼손 손가락 + 오른손 스타일러스 분업, Problem Statement 참고)를 그냥 포기하라는
  말과 같아 잘못된 조언이었다 — 0.0.6에서 그 문구를 빼고 순수 안내로만 남겼다.
  분업 UX를 살릴 수 있는지 두 가설을 실제 기기(갤럭시탭 P580/P610)에서 검증했고, **둘 다
  부정됐다**:
  1. (부정) 손가락을 먼저 누르고 있으면 그 홀드가 유지되는가 — 유지되지 않는다. 먼저 눌러
     둔 손가락도 펜이 다가오면 끊긴다. 게다가 손가락을 실제로 뗄 때 `pointerup`이 아예
     발생하지 않는다(`pointercancel`도 오지 않는다). 즉 브라우저 입장에서 그 손가락은
     "눌린 채로 영원히 남아 있는" 상태가 되고, 해제를 관찰할 방법이 없다.
  2. (부정) 터치 억제가 펜 근처 국소 영역에만 걸리는가 — 아니다. 화면 어디에 펜이 있든
     포인터가 보이는 동안에는 화면 전체에서 손가락 터치가 막힌다. 도구 모음을 멀리 배치해도
     완화되지 않는다.

  결론: 이 하드웨어에서 **"손가락으로 누른 채 유지 → 떼면 펜 복귀"라는 순간 지우개 메커니즘은
  성립할 수 없다.** 해제 이벤트가 오지 않으므로 복귀 조건 자체를 관찰할 수 없기 때문이다.
  현재 이 기기에서 순간 지우개는 사실상 토글처럼 동작한다(지우개를 누르면 지우개로 남고,
  펜 아이콘을 눌러야 펜으로 돌아온다). 남은 선택지는 기기 설정(삼성 S펜 포인터/호버 기능
  끄기)으로 호버 자체를 없애는 것, 또는 홀드 메커니즘을 걷어내고 토글로 단순화하는 것이다.
  **`0.0.10`에서 후자를 택했다** — `playground/momentary-eraser.ts`와 그 테스트를 제거하고
  도구 선택을 순수 토글로 바꿨다. 이 기기에서 이미 토글처럼 동작하고 있었으므로 실제 동작
  변화는 없고, 성립하지 않는 메커니즘을 떠받치던 코드(접촉 출처·식별자 추적, `touchType`
  분기, Touch 리스너 이중 배선)가 사라졌다.

- **S펜 측면 버튼도 막혔다(`0.0.13`에서 제거)**: 손가락이 안 되면 펜 하나로 해결하자는
  방향으로 측면 버튼을 조사했고, 버튼 입력이 웹까지 도달하는 것까지는 확인했다(`buttons`
  비트 1). 하지만 두 가지 이유로 쓸 수 없다.
  1. 비트 1은 **화면 접촉과 같은 비트**다. 버튼을 누른 상태에서는 화면에 닿아도 `buttons`
     값이 1에서 바뀌지 않아 `pointerdown`이 발생하지 않는다 — 즉 버튼을 누르고 있는 동안은
     그리기도 지우기도 되지 않는다. "누른 채 지우고 떼면 복귀"가 원천적으로 불가능하다.
  2. 차선책으로 "버튼 클릭 = 도구 토글"을 구현했으나, 실제로 버튼을 누르면 **삼성 시스템
     팝업(에어 커맨드)이 뜬다.** 웹 페이지가 막을 수 없는 OS 동작이라 이 방향은 종료했다.

  남은 후보는 하드웨어에 의존하지 않는 것들이다: 원샷 지우개(지우개 선택 → 한 획 지우고
  자동 복귀), 긁적여 지우기(빠른 왕복 획을 지우기로 해석). 둘 다 이벤트 가용성과 무관하므로
  대상 기기에서 확실히 동작한다.
